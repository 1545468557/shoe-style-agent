## 0. 项目性质（会影响后面每一条取舍）

**比赛项目，不是企业落地**：没有真实 PLM/ERP 数据、五个库都空、要求"尽量仿真"、交付重心是**能演示 + 架构站得住**（不是运营上线）。因此本声明的默认倾向是：**小、快、可演示、门禁与架构完整**，而不是"生产级完备"。

## 1. 产品形态判断

- **产品类型与核心任务**：多媒体创作 Agent——把一份企划（简报）做成**能打样、能落地**的设计方案：
  风格方向 → 款式设计（含出图）→ 面料/辅料选择 → 版型/工艺 → BOM 与尺寸表 → 打样审批。
- **核心交互**：**分阶段人工确认（五道门：简报 / 风格 / 面料 / 版型 / 打样审批）+ 多轮对话 + 动态工具调用**。
  人工确认与图片预览、任务恢复**属于产品核心体验**（不是"只看最后 JSON 就够"）。
- **开发路径**：**纵向切片**（按手册 §四：多轮对话 + 人工确认 + 可视化编辑类产品默认做最小纵向切片）。
- **当前阶段范围**：**阶段 1（本声明）**。下一步是阶段 2「后端 MVP」——先用**单品类（服装·连衣裙）**把主链路跑通：
  `企划 → 风格方向 → 款式设计（出图）→ 面料 → 版型 → BOM/尺寸表 → 打样审批`，五道门全部代码强制。

## 3. 触发的按需模块

| 模块 | 触发条件 | 现阶段是否引入 |
| --- | --- | --- |
| **SQLite + SQLAlchemy + Alembic** | 多实体关系（项目/方案/版本/款式/面料/版型/打样单）+ 人工确认 + 并发修改 | **引入**（本地 `data/`；上线前再评估 PostgreSQL） |
| **SSE** | 生成过程要逐步展示（出图排队、工具调用、阶段进度） | **引入**（事件序列以 `done` / `error` 收尾） |
| **本地文件目录存大图** | 出图产物是图片，不适合塞进数据库 | **引入**（`data/assets/`，按项目/方案分目录 + 原子写） |
| **python-docx / openpyxl** | 输出 BOM 与尺寸表（Excel）、方案文档（Word/PDF 前置） | **引入**（PDF 生成方式见 §4） |
| **Chroma（向量检索）** | 文档语义检索 / 知识库问答 | **暂缓**：仿真面料/鞋材库只有几百条，结构化字段 + 全文检索足够；规模或语义检索需求出现再引入 |
| **OCR** | 扫描件、图片文字 | **暂缓**：V1 输入是结构化企划与文本，没有扫描件需求 |
| **任务队列 / 后台任务** | 长耗时并发 | **暂缓**：内部试用、单进程够；改用"持久化任务记录 + 前台 SSE 进度" |

## 4. 偏离或暂缓的默认方案

| 默认方案 | 我们的做法 | 原因 | 影响 | 何时重新评估 |
| --- | --- | --- | --- | --- |
| Chroma 向量库 | 结构化仿真库 + SQLite 全文检索 | 数据量小（几百条），且字段化查询（品类/克重/成分/价格）比语义检索更准 | 无 | 语料上千条或出现"用自然语言找相似面料"的需求时 |
| 对象存储 | 本地目录 `data/assets/` | 内部试用、单机演示 | 换机器要搬目录 | 对外上线（阶段 4）时 |
| PostgreSQL | 先 SQLite | 单机、无并发写压力 | 迁移成本较小（SQLAlchemy + Alembic 已就位） | 多人同时编辑同一项目时 |
| 3D 虚拟试穿 / CLO3D | 不做，只在信息架构留位 | PRD §4.2 也说后续 | 演示少一个亮点 | 比赛若明确要求 3D 再评估 |
| 打样系统对接 | **仿真状态机**（草稿→审批→已推送→打样中→评审） | 无真实系统可对接 | 演示时须标注"仿真流程" | 有真实 ERP/PLM 接口时 |
| PRD 里的数字目标（≥30%、≥95%、+15pp） | 不写进验收硬标准，记"**待样例打分**" | 无基线（PRD 体检已裁决） | 首次真实冒烟后才有真数字 | 首次真实冒烟（5–10 条样例打分）后校准 D2/D3 |
| **对外表述** | 从"能用到库里真实存在的面料"改为"**具备接入企业真实物料库的完整门禁架构，当前演示使用示例库**" | 五个库都无真实数据，原话不能宣称（PRD 体检矛盾 6） | 卖点从"数据是真的"变成"架构建得对、接真库就能用" | 拿到真实物料库之后 |
